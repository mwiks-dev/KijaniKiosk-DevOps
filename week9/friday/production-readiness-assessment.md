# Production Readiness Assessment

The current KijaniKiosk deployment is production-approaching, but it is not yet suitable for handling real customer payment traffic. The three main concerns are external security, health signalling, and capacity management.

**External routing:** The current NGINX Ingress provides functional HTTP routing, but it is not adequate for production because kk-payments handles payment credentials without TLS. HTTP traffic is transmitted without encryption, meaning credentials and sensitive transaction data could potentially be intercepted between the client and Ingress. Production should terminate HTTPS at the Ingress using a Kubernetes TLS Secret containing the certificate and private key. The Ingress should reference that Secret through the `spec.tls` configuration and use the `nginx.ingress.kubernetes.io/ssl-redirect: "true"` annotation to redirect HTTP requests to HTTPS. Rate limiting is another important gap for a payment endpoint. NGINX Ingress can apply request limits using annotations such as `nginx.ingress.kubernetes.io/limit-rps`, reducing the risk of excessive requests overwhelming the service.

**Health signalling:** The current readiness and liveness probes provide basic protection, but their timing should be validated against the actual startup behaviour of kk-payments. If the service requires more than 15 seconds to establish database connections, initialise dependencies, or load application state, the current liveness `initialDelaySeconds: 15` may be too aggressive. A `startupProbe` should be considered so Kubernetes allows the application sufficient time to initialise before liveness checks begin. Readiness should also use a period and failure threshold that tolerate short-lived database or dependency delays without immediately removing healthy Pods from service. An excessively low `failureThreshold` could cause temporary database load to be interpreted as application failure, resulting in repeated restarts, connection churn, and potentially a restart cascade during an already degraded period.

**Capacity:** Three manually managed replicas are not a satisfactory solution for predictable end-of-month traffic spikes. Production autoscaling requires the Metrics Server to provide resource utilisation metrics, meaningful CPU and memory requests on the Deployment, and a HorizontalPodAutoscaler configured against those metrics. For example, an HPA could target CPU utilisation relative to the Pods' CPU requests and define sensible minimum and maximum replica counts. If the CPU target is set too high, Pods may become heavily loaded before the HPA reacts, causing increased latency, timeouts, and failed transactions. If the target is set too low, the HPA may scale out unnecessarily, increasing infrastructure costs and potentially causing replica churn. The target should therefore be established through load testing and observed production performance rather than selected arbitrarily.
